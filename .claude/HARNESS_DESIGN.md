## 1. 하네스 도입 배경

### 문제 인식

코드베이스에 새 기능을 추가할 때 반복적으로 발생하는 비효율이 있었다:

- 컨벤션 파일을 매번 수동으로 참조해야 함
- 구현 → 테스트 → 리뷰 순서가 사람마다 달라짐
- 코드 리뷰 전에 컨벤션 위반이 발견되는 경우가 많음
- PR 전 "이 파일 빠진 거 아닌가?" 를 매번 수동으로 체크

### 목표

**"요청 하나로 컨벤션을 준수한 코드와 테스트가 자동 생성되고, 리뷰까지 완료되는 파이프라인"**

단순 코드 자동완성이 아니라, 팀의 개발 프로세스 자체를 자동화하는 것이 목표다.

## 2. 핵심 설계 철학

### 2-1. 에이전트와 스킬의 분리

하네스에서 가장 중요한 설계 원칙이다.

| 구분       | 담는 것                                       | 비유     |
|----------|--------------------------------------------|--------|
| **에이전트** | 누가 하는가 — 역할, 작업 순서, 입출력 프로토콜, 에러 핸들링       | 직책 기술서 |
| **스킬**   | 어떻게 하는가 — 오케스트레이션 흐름, 에이전트 호출 방법, 지식·참조 자료 | 업무 매뉴얼 |

이 분리가 없으면 두 가지 문제가 생긴다:

1. **에이전트 재사용 불가** — `feature-development`와 `git-review` 둘 다 analyst·reviewer를 쓰는데, 역할 정의가 스킬에 묶여 있으면 중복 관리가 된다.
2. **역할 팽창** — 에이전트가 "어떻게 호출되는가"를 알아야 한다면, 에이전트 파일이 컨텍스트를 과도하게 담게 된다.

### 2-2. 단방향 의존성

데이터는 항상 한 방향으로 흐른다:

```
analyst → implementer
analyst → tester
implementer + tester → reviewer
```

에이전트가 서로를 직접 호출하거나 순환 참조하지 않는다. 이는 디버깅을 단순하게 만들고, 특정 에이전트만 재실행하는 부분 재실행을 가능하게 한다.

### 2-3. 지식의 계층화

```
00-domain-knowledge.md  ← 프로젝트 고유 도메인 (런타임 축적)
01~07-conventions.md    ← 팀 컨벤션 (변경 빈도 낮음)
agent.md                ← 에이전트 역할 (거의 불변)
SKILL.md                ← 오케스트레이션 흐름 (가끔 변경)
```

변경 빈도가 낮을수록 하위 레이어에 둔다. 도메인 지식은 기능이 추가될수록 자동으로 쌓이는 구조이므로 최상위에 분리했다.

## 3. 전체 작동 플로우

### feature-development (주 파이프라인)

```
사용자 요청 ("A 기능 추가해줘")
        │
        ▼
[Phase 0] 브랜치 준비 + _workspace 컨텍스트 확인
        │  ├── 새 기능 + 기반 브랜치 → back/feat/{name} 자동 생성
        │  └── 재실행/버그수정 → 현재 브랜치 유지
        ▼
[Phase 1] analyst (Opus, 순차)
        │  도메인 지식 + 컨벤션 읽기 → 코드베이스 탐색 → 구현 계획 수립
        │  출력: _workspace/01_analyst_output.md
        ▼
[Phase 2] implementer (Opus) ──┐ 병렬 팬아웃
          tester (Sonnet)      ┘
        │  implementer: 코드 구현 → 02_implementer_output.md
        │  tester: 테스트 작성 + 실행 검증 → 03_tester_output.md
        ▼
[Phase 3] reviewer (Sonnet, 순차)
        │  02 + 03 읽기 → 컨벤션 체크리스트 → 04_reviewer_output.md
        ▼
[Phase 3.5] 도메인 지식 업데이트
        │  새 Entity 추가 시만 → 00-domain-knowledge.md 갱신
        ▼
[Phase 4] 결과 종합 보고
```

**핵심 설계 포인트**: implementer와 tester를 병렬로 실행한다. tester는 analyst 출력(API 설계)만으로 테스트를 작성할 수 있기 때문이다. implementer 완료를 기다릴 필요가
없어 전체 실행 시간을 단축한다.

### git-review (리뷰 파이프라인)

```
/review 또는 "리뷰해줘"
        │
        ▼
[Phase 0] git 변경사항 수집 (오케스트레이터 직접)
        │  .claude/ 변경 여부 감지 → Phase 3.5 실행 여부 결정
        ▼
[Phase 1] analyst (Sonnet) — 변경 컨텍스트 분석
[Phase 2] reviewer (Opus)  — 컨벤션 체크리스트
[Phase 3] 커밋 메시지·구성 점검 (오케스트레이터 직접)
[Phase 3.5] 하네스 일관성 점검 (.claude/ 변경 시만)
[Phase 4] 종합 보고 (✅ / ⚠️ / 🚫)
```

## 4. 에이전트 설계 근거

### 에이전트를 4개로 분리한 이유

단일 에이전트로 "분석 → 구현 → 테스트 → 리뷰"를 모두 처리하면:

- 컨텍스트 오염: 분석 단계의 맥락이 구현 단계에 영향을 줌
- 책임 불명확: 오류 발생 시 어느 단계가 문제인지 추적 불가
- 재실행 비효율: 리뷰 이슈 하나를 수정해도 전체를 재실행해야 함

4개로 분리하면 **부분 재실행**이 가능하다. reviewer가 CRITICAL 이슈를 발견하면 implementer만 재실행하고, analyst·tester 결과는 유지한다.

### 각 에이전트 역할 경계

| 에이전트        | 하는 것               | 하지 않는 것       |
|-------------|--------------------|---------------|
| analyst     | 요구사항 해석, 파일 탐색, 설계 | 코드 작성         |
| implementer | 프로덕션 코드 작성         | 테스트 작성, 설계 변경 |
| tester      | 테스트 작성 + 실행 검증     | 프로덕션 코드 수정    |
| reviewer    | 기준 대조 체크           | 코드 수정 (발견만 함) |

reviewer가 코드를 직접 수정하지 않는 것이 중요하다. 수정까지 하면 "리뷰어가 구현을 검토한다"는 책임 분리가 무너진다.

## 5. 모델 선정 근거

### Opus vs Sonnet 분류 기준

단순히 "중요한 작업 = Opus"가 아니다. 판단 기준은 두 가지다:

1. **오류 전파 범위**: 이 에이전트의 실수가 얼마나 많은 downstream에 영향을 주는가
2. **작업 성격**: 깊은 추론이 필요한가, 아니면 명시적 패턴 대조인가

| 에이전트                  | 모델       | 근거                                                                        |
|-----------------------|----------|---------------------------------------------------------------------------|
| analyst (feature)     | **Opus** | 분석 오류 → implementer + tester 전체 재실행. 오류 전파 범위 최대                          |
| implementer           | **Opus** | 컨벤션 파일 6개를 동시에 준수하며 코드 작성. 실수 = 런타임 오류 직결                                 |
| tester                | Sonnet   | `@DataJpaTest` + `@Import` + `flush/clear` 패턴이 명확하게 정의됨. 틀려도 컴파일 훅이 즉시 감지 |
| reviewer (feature)    | Sonnet   | 명시적 체크리스트 기반 패턴 대조. 깊은 추론보다 꼼꼼한 대조가 핵심                                    |
| analyst (git-review)  | Sonnet   | 변경 파일 읽고 요약·누락 감지. feature analyst보다 단순한 작업                               |
| reviewer (git-review) | **Opus** | 하네스 일관성 점검(Phase 3.5) 포함. grep + 비교 추론 필요                                 |

### 비용 절감 효과

feature-development 한 번 실행 시:

- 변경 전: analyst(Opus) + implementer(Opus) + tester(Opus) + reviewer(Opus) = 4× Opus
- 변경 후: analyst(Opus) + implementer(Opus) + tester(Sonnet) + reviewer(Sonnet) = 2× Opus + 2× Sonnet

Sonnet은 Opus 대비 약 1/5 비용이므로 실질적인 절감이 발생한다.

## 6. 훅 설계 원칙

### 두 종류의 훅

| 훅                      | 이벤트                     | 역할                                      | 차단 여부           |
|------------------------|-------------------------|-----------------------------------------|-----------------|
| `post-test-compile.sh` | PostToolUse(Write/Edit) | 테스트 파일 작성 시 즉시 컴파일 확인                   | **차단** (exit 2) |
| `stop-test-absence.sh` | Stop                    | 새 Service/Controller 추가 시 Test 파일 누락 경고 | 비차단 (경고만)       |

**왜 컴파일만 체크하고 테스트 실행은 안 하는가?**

테스트 실행은 DB 연결이 필요하고 수십 초가 걸린다. 에이전트가 파일을 한 번 쓸 때마다 테스트를 실행하면 전체 파이프라인이 느려진다. 컴파일 오류는 즉시 잡고, 실제 실행은 tester 에이전트가 작업 완료 후
명시적으로 수행하는 책임 분리를 선택했다.

**왜 테스트 누락 경고는 비차단인가?**

경우에 따라 테스트를 의도적으로 나중에 추가하는 경우가 있다 (부분 재실행, 임시 브랜치 등). 차단으로 설정하면 정상적인 워크플로우를 방해한다. 경고로 충분히 인지시킬 수 있다.

## 7. 도메인 지식 관리 전략

### 왜 별도 파일인가

초기에는 `analyst.md`에 도메인 정보를 넣는 것을 검토했으나 두 가지 이유로 거부했다:

1. **에이전트/스킬 분리 원칙 위배**: 도메인 지식은 역할이 아니라 지식이므로 references에 있어야 한다
2. **재사용성**: analyst만이 아니라 reviewer, tester도 도메인 맥락을 참조해야 할 수 있다

### 자동 업데이트 설계

`feature-development` Phase 3.5에서 새 Entity가 추가된 경우에만 `00-domain-knowledge.md`를 갱신한다.

**업데이트 조건을 "새 Entity 추가 시만"으로 한정한 이유**: Service/Controller만 추가되는 경우는 도메인 구조가 바뀌지 않는다. 매번 갱신하면 파일에 노이즈가 쌓인다.

## 8. 평가 프레임워크 설계

### 왜 정적 지표를 선택했는가

RAG 챗봇처럼 "실제 실행 후 정답 비교" 방식을 먼저 검토했다. 하지만 하네스는 RAG와 근본적으로 다르다:

|       | RAG 챗봇      | 하네스             |
|-------|-------------|-----------------|
| 출력    | 텍스트 (비교 가능) | 코드 파일 (정답 없음)   |
| 비결정성  | 낮음          | 높음              |
| 실행 비용 | 저렴          | 고비용 (에이전트 여러 개) |

"20개 기능 요청을 실행해서 채점"하는 방식은 높은 비용과 비결정성으로 인해 재현성이 낮다.

대신 **하네스 파일 자체를 분석하는 정적 지표**를 선택했다. 실행 비용이 0이고, 하네스가 변경될 때마다 즉시 측정 가능하며, 버전 간 비교가 가능하다.

### 5개 카테고리 도출 근거

| 카테고리        | 측정 대상              | 가중치 근거                      |
|-------------|--------------------|-----------------------------|
| A. 프롬프트 완전성 | 에이전트가 혼자 작동할 수 있는가 | 기초 조건                       |
| B. 컨텍스트 체인  | 파이프라인이 끊기지 않는가     | 런타임 오류 직결                   |
| C. 일관성      | 파일 간 모순이 없는가       | 가중치 최고 — 불일치는 예측 불가능한 동작 야기 |
| D. 가드레일     | 자동 안전망이 있는가        | 품질 하한선 보장                   |
| E. 컨벤션 참조   | 에이전트가 충분한 지식을 가지는가 | 출력 품질 직결                    |

C(일관성)에 가중치 25%를 부여한 이유: 에이전트 정의와 스킬 프롬프트가 불일치하면 에이전트가 어느 쪽 지시를 따를지 예측할 수 없다. 이는 조용한 버그로 이어진다.

### git-review와의 통합

하네스 일관성 점검을 별도 명령이 아닌 `git-review`(Phase 3.5)에 통합한 이유:

- 하네스 파일은 코드와 함께 변경되는 경우가 많다
- PR 전에 코드 리뷰와 하네스 점검을 동시에 받는 것이 자연스럽다
- `.claude/` 변경이 없으면 해당 Phase를 건너뛰므로 오버헤드가 없다

## 9. 채택하지 않은 대안

### 9-1. Scenario/Piece 인수 테스트

초기 하네스에는 RestAssured 기반 Piece Test + Scenario Test가 포함되어 있었다.

**제거 이유**:

- `@SpringBootTest` + `@DirtiesContext` 조합은 컨텍스트 로드 시간이 길다
- 실제 서버를 띄워야 하므로 CI 환경 의존성이 높다
- `@DataJpaTest` 기반 Service Test로 동일한 통합 커버리지를 더 빠르게 달성 가능

### 9-2. 모든 에이전트에 Opus

초기 설계는 모든 에이전트가 Opus였다. 비용 분석 후 Sonnet으로 대체 가능한 에이전트를 식별했다.

**기준**: 훅(컴파일 체크)이나 명시적 체크리스트가 안전망 역할을 하는 에이전트는 Sonnet으로 내려도 된다. 안전망이 없는 analyst(feature)와 implementer는 유지했다.

### 9-3. Stop 훅 기반 하네스 자동 평가

`.claude/` 파일이 변경될 때마다 Stop 훅이 자동으로 일관성 체크를 실행하는 방안을 검토했다.

**채택하지 않은 이유**:

- 훅은 셸 스크립트이므로 복잡한 일관성 로직을 구현하기 어렵다
- 하네스 파일을 수정하는 모든 세션마다 훅이 실행되면 불필요한 오버헤드가 발생한다
- git-review와 통합하는 방식이 "PR 전 최종 검증"이라는 맥락에 더 잘 맞는다

### 9-4. 도메인 지식을 analyst.md에 직접 포함

analyst가 가장 먼저 읽는 파일이므로, 도메인 지식을 analyst.md에 직접 작성하는 방안을 검토했다.

**채택하지 않은 이유**:

- 에이전트/스킬 분리 원칙 위배 (역할 파일에 지식을 담으면 안 됨)
- 도메인이 추가될 때마다 agent 파일을 수정해야 하는 유지보수 부담
- reviewer, tester도 도메인 맥락이 필요해질 수 있으므로 공유 references로 관리하는 것이 맞다

### 9-5. 에이전트별 전용 모델 파일 분리

`analyst-opus.md`, `analyst-sonnet.md` 식으로 모델별 에이전트를 분리하는 방안을 고려했다.

**채택하지 않은 이유**:

- 역할은 동일하고 모델만 다른 파일을 두면 중복 관리 문제가 생긴다
- 모델은 SKILL.md 호출 시점에 `model:` 파라미터로 제어하는 것이 더 유연하다

## 10. 확장 포인트

### 10-1. 동적 평가 (실행 기반 채점)

현재 평가는 정적 지표만 측정한다. 다음 단계는 **표준 기능 요청 20~30개를 정의하고 실제 실행 결과를 채점하는 동적 평가**다.

```
난이도 S (30%): 단순 CRUD — "User 조회 API 추가해줘"
난이도 A (40%): 도메인 로직 — "Host가 세션 종료 시 참가자 알림"
난이도 B (30%): 도메인 간 연관 — "User가 Host로 전환하는 기능"
```

채점 항목: 컴파일 성공 / reviewer CRITICAL 0건 / 테스트 존재 / 도메인 지식 업데이트

### 10-2. 멀티 리뷰어 (관점 분리)

현재 reviewer는 컨벤션 + 보안 + 성능을 하나의 에이전트가 담당한다. 트래픽이 늘어나면:

- `reviewer-convention.md` — 컨벤션 전용
- `reviewer-security.md` — 보안 취약점 전용
- `reviewer-performance.md` — N+1, 인덱스 전용

으로 분리해 병렬 실행할 수 있다.

### 10-3. 히스토리 기반 패턴 학습

`_workspace_prev/`에 이전 실행 결과가 보존된다. 이를 분석하면:

- 자주 발생하는 CRITICAL/MAJOR 이슈 → 컨벤션 파일 보강
- analyst가 자주 틀리는 도메인 → 도메인 지식 파일 보강

수동으로라도 `_workspace_prev/`를 주기적으로 분석해 하네스를 개선하는 루프를 만들 수 있다.

### 10-4. CI/CD 연동

현재 하네스는 로컬 Claude Code에서만 실행된다. GitHub Actions에 연동하면:

- PR 생성 시 자동으로 git-review 실행
- 하네스 일관성 점검 결과를 PR 코멘트로 포스팅

### 10-5. 도메인 지식 자동 검증

`00-domain-knowledge.md`에 기록된 도메인 목록과 실제 코드베이스의 Entity 목록을 비교해 불일치를 감지하는 훅을 추가할 수 있다.

## 11. 도입 전후 비교

하네스를 설계하면서 자동화된 항목과 그 전에 수동으로 처리하던 방식을 비교한다.
실행 횟수 기반 수치는 아직 측정 전이므로, 제거된 수동 작업 항목 기준으로 정리한다.

### 제거된 수동 작업

| 항목           | Before (수동)                    | After (자동화)                            |
|--------------|--------------------------------|----------------------------------------|
| 브랜치 생성       | 매번 직접 `git checkout -b`        | Phase 0에서 kebab-case 브랜치 자동 생성         |
| 컨벤션 파일 참조    | 7개 파일을 수동으로 열어 확인              | 에이전트가 레이어별로 필요한 파일만 선택 읽기              |
| 구현 → 테스트 순서  | 사람마다 다름, 누락 자주 발생              | Phase 2 병렬 실행으로 항상 동시 생성               |
| 테스트 파일 누락 감지 | PR 리뷰 시점에 발견                   | Stop 훅이 Claude 응답 종료 시마다 감지            |
| 컴파일 오류 확인    | 수동 `./gradlew compileTestJava` | PostToolUse 훅이 테스트 파일 저장 시 자동 실행       |
| 코드 리뷰 체크리스트  | 리뷰어 재량에 따라 깊이 다름               | CRITICAL/MAJOR/MINOR 기준 고정 체크리스트       |
| 도메인 구조 파악    | 신규 기능 작업 시 코드 탐색 반복            | `00-domain-knowledge.md` 누적으로 탐색 시간 단축 |

### 모델 비용 변화

초기 설계는 모든 에이전트가 Opus였다. 작업 성격 분석 후 Sonnet 전환 가능한 에이전트를 식별했다.

```
Before: analyst(Opus) + implementer(Opus) + tester(Opus) + reviewer(Opus) = 4× Opus
After:  analyst(Opus) + implementer(Opus) + tester(Sonnet) + reviewer(Sonnet) = 2× Opus + 2× Sonnet
```

Sonnet은 Opus 대비 약 1/5 수준이므로, feature-development 한 번 실행 기준으로 에이전트 호출 비용이 약 절반으로 줄었다.

## 13. 설계 과정에서 발견·수정한 이슈

하네스를 설계하고 점검하는 과정에서 아래 문제들을 발견했다. 정적 평가 프레임워크가 이런 종류의 불일치를 잡아내기 위해 만들어진 것이기도 하다.

### 발견된 불일치 목록

| 이슈                             | 발견 방법                                                  | 수정 내용                                                         |
|--------------------------------|--------------------------------------------------------|---------------------------------------------------------------|

### 핵심 교훈

**에이전트 파일과 스킬 프롬프트는 별도 파일이므로, 한쪽을 수정했을 때 다른 쪽이 자동으로 따라오지 않는다.** 이것이 C 카테고리(일관성)를 평가 지표에서 가중치 25%로 가장 높게 설정한 이유다.

또한 도메인명 같은 프로젝트 고유 명칭은 하네스 파일 전체에 퍼지기 쉽다. 초기 설계 시부터 고유 명칭 대신 범용 용어(`{Domain}`, "백엔드")를 쓰는 것이 이후 유지보수 비용을 줄인다.

## 14. 한계 및 주의사항

### 비결정성

LLM 기반 에이전트는 동일한 입력에 다른 출력을 낼 수 있다. 특히:

- analyst의 파일 탐색 범위가 달라질 수 있음
- implementer의 구현 방식이 실행마다 조금씩 달라질 수 있음

정적 평가 프레임워크가 하네스 설계의 품질을 보장하지만, 실행 결과의 일관성은 보장하지 않는다.

### 컨텍스트 길이 제한

`_workspace/` 파일들이 쌓이면 에이전트의 컨텍스트를 많이 차지한다. 장기 프로젝트에서는 `_workspace_prev/`를 주기적으로 정리하는 것이 권장된다.

### 하네스 파일 유지보수 부담

하네스 자체도 코드다. 컨벤션이 바뀌면 references 파일을, 에이전트 역할이 바뀌면 agent.md를 수동으로 업데이트해야 한다. `HARNESS_EVAL.md`의 체크리스트를 하네스 수정 후 항상 실행하는
습관이 필요하다.
